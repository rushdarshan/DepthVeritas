# Multi-Head Extension Framework for Depth Anything V2

## Problem Frame

Depth Anything V2 provides a powerful DINOv2-based backbone for monocular depth estimation, but the official repo bakes in a single relative-depth prediction head. The DA2 paper lists 5+ natural extension paths (metric depth, uncertainty estimation, video temporal consistency, surface normals, edge detection), each requiring different decoders, loss functions, datasets, and evaluation metrics. Without a framework, each extension becomes a standalone fork with duplicated training loops, dataloaders, checkpointing, and metric code — making a unified "5+ heads" technical report infeasible in an 8-week window.

A shared framework lets the first head pay the infrastructure cost; subsequent heads add only head-specific code (decoder, loss, metrics). It also produces a DINOv2 Feature Ablation Atlas as a natural byproduct — the shared eval harness can freeze the backbone and probe which feature layers matter for each task.

**Goal:** Framework in 2 weeks, 5+ head experiments in remaining 6 weeks.

---

## Requirements

- **R1. Shared backbone loading.** Load pretrained DA2-Small weights from the official checkpoint. Backbone frozen by default. Support configurable LoRA adapters on attention projections (rank=8 default) as the sole trainable backbone parameters.

- **R2. Pluggable head interface.** Abstract `BaseHead(torch.nn.Module)` defining `forward(self, features: list[Tensor]) -> dict` (returns dict for per-head structured output), `compute_loss(self, preds, batch) -> Tensor`, and `compute_metrics(self, preds, batch) -> dict[str, float]`. Each head is a single file under `heads/<name>.py` — no registration boilerplate beyond adding it to a config.

- **R3. Config-driven training harness.** Single YAML/JSON config specifies: head type, dataset(s), backbone LoRA rank, optimizer (AdamW default), learning rate, batch size, fp16, gradient accumulation steps, max epochs, checkpoint path. No code changes to switch experiments.

- **R4. Dataloader registry.** Pluggable dataset configs keyed by name. Built-in: KITTI (metric depth), NYUv2 (relative depth + normals), DIODE (metric depth), Sintel (video consistency), BSDS500 (edges). Each dataset entry specifies root path, split, image size, and transforms. Training harness resolves by name from config.

- **R5. Metric suite.** Shared evaluation functions computed per-head/output-type. Relative depth: AbsRel, δ1/δ2/δ3, RMSE. Metric depth: AbsRel, δ1/δ2/δ3, RMSE, SILog (scale-invariant log). Uncertainty: ECE, AUSE, sharpness. Temporal consistency: flow-warped photometric error, flicker. Surface normals: mean angular error, correct predictions @ 11.25°/22.5°/30°. Edges: F-measure (ODS/OIS), precision, recall.

- **R6. Experiment tracking.** Per-run logging to console + TensorBoard (scalars, histograms, config snapshot). Checkpointing saves backbone and head separately to a versioned directory — head-only checkpoints are small; backbone is persisted once and shared across experiments. Resumption from latest checkpoint.

- **R7. Visualization suite.** Depth map color rendering (turbo colormap, percentile normalization). Failure-mode overlay (plot error map side-by-side with prediction + ground truth). Video side-by-side for temporal models: stacked frames with prediction + uncertainty + error. Comparison grid: one scene across all 5+ heads, or one head across all datasets.

---

## Success Criteria

1. Framework supports 5+ head types from a single `train.py --config experiment.yaml` entry point.
2. Adding a new head requires ≤100 lines of new code (decoder + loss + metrics) and zero changes to shared infra.
3. First head (relative depth) matches DA2 paper results on NYUv2 within ±1% AbsRel after 2 weeks of framework dev.
4. Heads 2-5 are running within 6 weeks total: each ≤1 week of head-specific work.
5. Backbone is loaded once and shared across all experiments in the same checkpoint root.
6. DINOv2 Feature Ablation Atlas can be generated by running the relative-depth head eval with `--ablate_feature_layer <n>` for each DINOv2 block.

---

## Scope Boundaries

**In scope:**
- DA2-Small backbone only (ViT-S). DA2-Base/Large are config changes, not structural work.
- Supervised training heads only (no RL/self-supervised losses).
- Single-GPU training (DDP is a future extension).
- LoRA adapters; full fine-tuning is a config flag away but not the primary path.

**Out of scope (v1):**
- Multi-head joint training (one model predicting all outputs simultaneously).
- Distillation from a larger teacher.
- Mobile / ONNX / TensorRT export.
- Web demo or Gradio interface.
- Automated hyperparameter search.

---

## Key Decisions

- **Head interface returns `dict`** not positional tuples. This keeps forward signatures stable as heads evolve (e.g., uncertainty head returns `{"depth": ..., "uncertainty": ...}`; adding a new output key doesn't break callers).
- **Config-driven, not code-gen.** A Python dataclass registry pattern (decorator on each head + each dataset) rather than YAML-to-code generation. Keeps introspection simple and IDE-friendly.
- **Head and backbone saved separately.** At iteration end, write `backbone.pt` (once, skipped if exists) and `head-{head_name}-ep={epoch}.pt`. This lets the shared backbone blob serve all experiments without per-experiment duplication.
- **LoRA applied at the framework level**, not inside each head. The config `backbone.lora_rank: 8` injects adapters into backbone attention after loading. Head code never touches backbone internals.
- **Single `train.py` entry point.** No separate scripts per head. `train.py --config X.yaml` routes to the right head, dataset, and hyperparams. Avoids the common anti-pattern of `train_metric_depth.py` + `train_uncertainty.py`.

---

## Dependencies / Assumptions

- **PyTorch ≥2.0, torchvision, timm** (for ViT components not already in DA2). Dependencies match DA2 official repo with minimal additions (adds `tensorboard`, `pyyaml`, `einops`).
- **Pretrained DA2-Small checkpoint** is downloaded and available at a configurable path. We do not train the backbone from scratch.
- **Datasets are user-provided** at local paths configured per experiment. Framework does not bundle data.
- **LoRA implementation:** we reuse the `lora.torch` integration (or a small inline `LoRALinear` module) rather than pulling in PEFT as a dependency — keeps dep surface minimal.
- **2 contiguous weeks** for framework implementation before any experiments begin.

## Outstanding Questions

- Q1. Should we support per-head `forward()` returning a dict vs. a namedtuple? Dict is more flexible; namedtuple is easier to type-check. Decision is R2's dict return unless profiling shows meaningful overhead.
- Q2. Should the framework export to a pip-installable package, or remain a repo with `train.py` at root? For v1, repo with `train.py` root is sufficient — reduces packaging overhead. Revisit if collaborators join.
- Q3. How to handle dataset download / preparation scripts? Build `scripts/prepare_{dataset}.py` or document manual steps? Decision: document manual steps + pointer to each dataset's official download. Preparation scripts add maintenance burden for rarely-changed data.
- Q4. Should the DINOv2 Feature Ablation Atlas be a CLI flag or a separate script? Decision: CLI flag `--ablate-layer` on `eval.py` — simpler for interactive probing.
